## Story

As a captain,
I want to choose the four consumables my ship can carry before I sail,
so that the game only ever offers me the consumables I actually want, on keys 1–4.

**Eric's thought (2026-10-25, verbatim):** *"Go back down to 4 consumable slots, make what each slot holds player-configurable so that the game only gives you those consumables."* Ruled the same day (epic-10 amendment 1c): configured on the port screen as a CONSUMABLES row in amendment 96's key · value grammar, saved in localStorage like the callsign; **keys return to 1–4**. Corrected 2026-10-27 (amendment 2): no LOADOUT screen exists — this story BUILDS the row on the class-select layer. Supersedes Story 9.2's six fixed keys (epic-9 amendments 31–38) for the slot count and the key row.

## Dev Notes

### Scope, in one line

A global kind → slot map becomes a per-ship four-long kit chosen on the port footer, carried as a join option like the gun, held on `ShipRecord`, sent back self-privately on `OwnShip`, and used as the one gate (`pickRefusal`) that confines the draw and the drone drops; the belt is four wide; the countermeasure line is called SMOKE SCREEN again.

### The one gate (read before touching draw.ts or world.ts)

`pickRefusal(held, slotIds, lineId, kit)` already refuses a consumable that has no slot as `'stub'` (`boons.ts:330`). With the kit in hand, "no slot" ⇔ "not in the kit", so the draw (`eligibleLines`, `usableLines`), the spend (`refusesCard`, `spendCard`), the bots (`spendableIndices`) and the drone drops (`pickDrop` builds its eligible list with `!refusesCard`) are ALL confined by the same function. Do not add a second filter anywhere; do not coin a new refusal word (`'stub'`'s meaning — "no slot for this line" — is exactly right and the client greys nothing for it because the line is never dealt). The level-zero guarantee stays vacuous-safe: `usableLines` is never empty because the kit always holds four dealable lines.
