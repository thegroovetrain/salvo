# CLAUDE.md

## Project

Hullcracker is a real-time, gridless naval battle royale in the browser. One ship per player on a large circular ocean with islands. Everyone fights on the same water in real time: an authoritative 20Hz server simulation with client-side prediction. Two-tier fog of war (a true-sight bubble around your hull plus a rotating radar sweep that paints decaying phosphor blips over height-aware terrain shadows), gun/torpedo/mine/star-shell/broadside/radar-buoy fits with real firing arcs, XP-banked levels spent on boon cards, and a storm circle that shrinks and finally collapses. Last hull floating wins. This IS `main`: the real-time rebuild replaced the previous turn-based hex game at v0.16.0, and that game survives only in git history and `CHANGELOG.md`. See README.md for the player-facing overview.

Stack: TypeScript monorepo (npm workspaces) — `shared` (pure sim), `server` (Colyseus 0.17), `client` (PixiJS 8 + Vite).

### Commands
```
npm run dev          # Colyseus server (:2567) + Vite client (:5173) via concurrently
npm run check        # lint + type-check (shared/server/client) + all tests (5716: 784/1702/3230)
npm run lint         # ESLint (complexity=10 enforced)
npm test -w shared   # Shared sim tests (kinematics, geometry, ballistics, zone, mapgen, stats, boons/deck/offers, radar shadow, wake)
npm test -w server   # Server tests (world sim, perception/anti-cheat invariants, match + queue, PvE fleet, bots)
npm test -w client   # Client tests (prediction, snapshots, clock, HUD/feel pure logic)
npm run build        # Build order: shared → client → server
```

- The server game process listens on `:2567` (override with `PORT`); the Vite client dev server is `:5173`. Open the client URL in the browser.
- **Server must boot from `server/`** (or `--tsconfig server/tsconfig.json`): Colyseus schema decorators need that tsconfig.
- **Headless smokes** in `server/scripts/*.mjs` prove full flows over real sockets. They use dev-only room options the server only honors when `HC_DEV_OPTIONS=1` is set — production clients can never pass them.

### Architecture

Three workspaces with strict layering: `shared` (deterministic pure simulation, imported by both sides) → `server` (authoritative world + Colyseus room) and `client` (prediction + Pixi renderer). Both sides run the SAME shared sim functions, which is what makes client-side prediction match the server.

#### Shared (`shared/src/`) — deterministic sim, zero I/O, plain objects
- **index.ts** — single barrel re-export; declares `PROTOCOL_VERSION` (bumped on any wire-contract break) and carries the dated wire-change log.
- **constants.ts** — `CONFIG`: the single source of truth for every simulation tunable (map, three ship classes, vision/eighths ladder/sweep, every equipment row, XP + offer economy, damage control, storm zone timeline, bounty, PvE fleet, bot competence, transport rate limit under `net`). Also `REGATTA_HUES` (the 20-hue wheel — wire identity is the INDEX). The 14-entry legacy `UPGRADE_IDS` / `UPGRADE_CATEGORIES` / `CONFIG.upgrades` system is GONE; `HEAL_CHOICE` lives in types.ts and the boon catalog in sim/boons.ts.
- **types.ts** — the client/server wire contract: `InputMsg`, `SpendMsg`, `FrameMsg`, `OwnShip`, `Contact`, blip/wake events, the 18 `GameEvent` kinds, `MineView`/`LitZoneView`/`BuoyView`, `MSG` channel names, `WelcomeMsg`/`ResultsMsg`, `HEAL_CHOICE`.
- **math/** — vec.ts, angle.ts (`wrapPositive`), geom.ts (`segCircleHit` — the LOS primitive), rng.ts (`mulberry32` seeded RNG).
- **sim/ship.ts** — ship kinematics (`stepShip`, `ShipConfig`, hull endpoints).
- **sim/stats.ts** — `effectiveStats()`: THE server/client desync firewall. One pure function turns (ship class + fitted boons) into every derived number the sim and HUD consume, folding boon stat effects and re-pinning every DERIVED field post-fold (`sightRange`, the `rangeU` paths, `cooldownScale`, `mine.triggerRadius`). Both sides MUST call it; nothing re-derives a boosted stat ad hoc.
- **sim/boons.ts** — the boon effect engine + THE CATALOG. A boon is one card LINE `{id, category, rarity, copies, effects[]}`; `stat` effects flow only through `applyBoonStats` and `doctrine` effects fold into per-weapon VERB FLAGS on `EffectiveStats` (verbs stack — exclusivity is deleted). `BOON_STAT_PATHS` is the whitelist of addressable stat paths.
- **sim/deck.ts** — THE DECK MODEL: a player's deck is the universal lines + one subdeck per carried equipment + one acquisition card per not-carried acquirable equipment. `drawOffer` only READS the pool; exactly one card leaves on `consumeCard`.
- **sim/offers.ts** — `BoonOffer`: the wire-facing shape of the front level's drawn card ids, materialized once and held server-side so reopening the refit window can NEVER reroll (FR19).
- **sim/loadout.ts** — the 4-slot equipment loadout every fitted system builds on, `EquipmentId` / `EQUIPMENT_IS_WEAPON`, and the per-hull fit: TB `[gun, torpedo, speedBoost, —]`, BS `[gun, broadside, starShells, —]`, ML `[gun, mine, radarBuoy, —]`; PvE fleet hulls keep the universal `[gun, torpedo, mine, —]`.
- **sim/arcs.ts** — THE single arc-shape source: gun family 360°, torpedo bow sector, mine + radar buoy rear sector, broadside twin beam sector. The server's launch checks and the client's arc render read the same function.
- **sim/aim.ts** — the shared truth about where a shot STARTS and ENDS (hull clearance, muzzle spawn, map clamp, burst point), so the client's aim preview IS the server's resolution.
- **sim/spread.ts** — the ONE straddle rule (`straddleOffsets`) for any evenly-spaced ladder about a centre, so server resolution and per-shell client preview cannot diverge. Two consumers: BARREL's parallel gun tracks, and the BROADSIDE's turret MUZZLES + MOUNT BEARINGS — it spaces the GUNS, not the shells (the broadside's authored angular fan was deleted at cycle 114).
- **sim/collision.ts** — boundary + ship-island resolution, plus `applyGroundingDamp` (the stateless head-on-scaled speed cap both sides fold).
- **sim/boost.ts** / **sim/slow.ts** — the two per-tick kinematics hooks (speed boost's forward-cap raise; PROP-FOULING's both-caps slow), each called identically by the server's `stepShips` and the client's prediction/replay.
- **sim/hooks.ts** — `HOOK_REGISTRY`: the behavior-hook leg of the boon engine (pure; exactly one attachment point — per-tick kinematics).
- **sim/lifecycle.ts** — THE one representation of a hull's life and death (`afloat` / `sinking` / `sunk`, with timestamps). It REPLACED `ShipRecord.alive: boolean`, never shadowed it.
- **sim/sinking.ts** — the sinking window's motion + deadline math: the linear speed cap both sides fold at the same 50ms dt.
- **sim/shell.ts** — swept ballistic collision (`stepShell`).
- **sim/map.ts** — seeded deterministic HEIGHT-FIELD map generation (`generateMap`): builds the fBm field, rank-selects sea level, extracts coastlines and render-only contours, and runs the navigability-grid validator; islands never travel on the wire, both sides rebuild the identical polygon coastlines (and height raster) from the seed.
- **sim/noise.ts** — integer-hashed permutation-table gradient noise, fBm, ridged multifractal, and a two-scale domain warp. Zero transcendentals (no `sin`/`cos`/`pow`/`exp`/`hypot`) so the field is byte-identical across V8/JavaScriptCore and `--jitless`/`--no-opt`.
- **sim/heightField.ts** — builds the height field (coarse pass + coastal-band refinement), the quantized Uint8 raster, and the max-height pyramid; O(1) sample + per-tile-ceiling API. CONSUMED by sim/radarShadow.ts since Story 4.11.
- **sim/islandShape.ts** — the extraction machinery: per-map scratch grid, sea-level mask, lagoon closure (flood open water from the spawn ring, fill what it can't reach), marching-squares tracing.
- **sim/island.ts** — the single geometry seam every island consumer uses (LOS, shells, mine legality, spawn clearance, AI avoidance, collision push-out): mandatory bounding-circle broadphase (`isle.x/y/r`) before any exact polygon test, delegating all polygon math to `silhouette.ts`.
- **sim/silhouette.ts** — THE single hull-geometry source (the silhouette IS the hitbox): one closed local-frame polygon per hull id, plus the ONE polygon library every island/ship test delegates to.
- **sim/radarShadow.ts** — the ONE height-aware terrain-occlusion model: an ACCUMULATING ray fold whose root IS the reach. `visibilityTo()` is the server's radar gate; `requiredHeight()` is the client's terrain-paint instance of the same unification.
- **sim/radarRaster.ts** — THE hull raster: projects a true hull polygon onto the low-resolution radar lattice and fuzzes it into a return. The server builds the wire footprint from it; the client rasterizes sighted contacts from it.
- **sim/wake.ts** — the ONE wake model: the server's per-tick sampler + per-segment disclosure gate, and the client's on-water and radar ribbons.
- **sim/zone.ts** — phased storm timeline (`zoneStateAt`/`zoneLiveState`/`rollZoneRings`/`isOutside`): FOUR ring groups × clear/supply/reveal/close beats (the fourth is sudden death), offset-center rings (server-rolled, reveal-gated), terminal radius derived from truesight, then a concentric collapse to r=0 — fully closed at 16:00.

#### Server (`server/src/`)
- **index.ts** — `@colyseus/tools` boot; listens on `PORT` or `:2567`.
- **app.config.ts** — Colyseus app config; registers BOTH rooms — `queue` (`StandardQueueRoom`) and `arena` (`ArenaRoom`) — and mounts `/metrics` + `/liveness` through one `createRouter` call.
- **log.ts** / **metrics.ts** / **liveness.ts** / **robots.ts** / **stagingGate.ts** — ops surfaces, NOT sim: structured stdout logging, process-local counters behind `GET /metrics`, the public `GET /liveness` presence read (sourced from `matchMaker.query()`, so it stays correct the day the game runs on more than one node), the `HC_NOINDEX=1` search-engine guard that keeps the staging host out of the index (`X-Robots-Tag: noindex, nofollow`, mounted ahead of `express.static`; never mounted in production), and the `HC_STAGING_KEY` shared-password gate — the ONE ops surface with two halves, because the two doors into this app run on different stacks: an Express middleware for the page, and `stagingGateError()` called from BOTH rooms' `static onAuth` for matchmaking (Express never sees `/matchmake/*`). Both inert unless their env var is set.
- **rooms/StandardQueueRoom.ts** — the standard-match queue: a thin Colyseus adapter (pool array, socket sends, matchMaker calls) over the pure policy in queue.ts. It sits IN FRONT of the arena so "which mode am I waiting for" is never a property of the arena room.
- **rooms/queue.ts** — the queue's arm/form POLICY: pure functions over plain numbers, zero Colyseus imports (the world.ts / match.ts posture).
- **rooms/ArenaRoom.ts** — thin Colyseus adapter around `World` + `Match`. Bridges joins/leaves → roster schema, raw `"i"` input messages → World's input store, fixed steps → per-client frames. Applies the transport rate limit (`CONFIG.net.maxMessagesPerSecond`), gates dev room options behind `HC_DEV_OPTIONS`, and is the ONLY file that knows the word "solo" (it builds the 19-bot fleet).
- **rooms/roomOptions.ts** — `sanitizeRoomOptions()`: security gate for client-supplied room options, including the `PROTOCOL_VERSION` join gate (`protocolVersionError`).
- **rooms/schema/ArenaState.ts** — Colyseus `@type` schema (roster / `PlayerMeta`, the revealed zone rings, `matchPhase`, `bountyId`); only these sync via schema — all spatial state flows through frames instead.
- **game/world.ts** — the authoritative simulation. Plain TS, ZERO Colyseus imports (fully unit-testable). Owns the single server clock; runs a 20Hz (50ms) fixed tick over the declared, order-pinned `STEP_ORDER` table: fleet + bot inputs → applyInputs → stepShips → resolveCollisions → sampleWakes → founderSinking → applyStorm → stepShells → stepMines → tickBuoys → applyZoneEffects → tickRepairs → tickSmoke → expireLitZones → fire/activation/horn control → advanceSweeps → processRespawns → tickXp → spawnFleetWaves.
- **game/perception.ts** — per-observer visibility: the fog-of-war core and anti-cheat boundary (`observe()` / `observeSpectator()`). The eighths-ladder vision tiers, island LOS, height-aware radar shadowing, and per-event visibility rules. Property-style invariant tests enforce that nothing outside sight ∪ this-tick radar paints can appear in any frame — save the SIX declared exceptions (`sp`, `hc`, `mz`, `sunk`, `sm`, `fh`) and the jamming-buoy fakes carve-out.
- **game/signals.ts** — THE signal registry: one declarative row per spatial channel (every `GameEvent` kind plus the contact-like `contact` / `mine` / `litzone` / `buoy` channels), each owning its `visible()` and `materialize()`. perception.ts is the ONLY caller; nothing spatial leaves the server outside a row.
- **game/frames.ts** — per-client frame construction; the single chokepoint for everything spatial leaving the server. Contacts/events come EXCLUSIVELY from `perception.observe()`.
- **game/inputs.ts** — input validation + latest-input store; the only path player intent enters the sim. Malformed messages are silently dropped (every field finite-checked, axes clamped).
- **game/match.ts** — match lifecycle state machine (waiting/gathering/countdown/live/results). Pure logic, zero Colyseus imports; the room implements its side-effect hooks.
- **game/participants.ts** — THE ship-role seam: `isHuman` (`role === 'captain'`), `isParticipant` (`role !== 'fleet'`), `isFleetHull` — the three readings that used to be one `isDrone` boolean.
- **game/drones.ts** — the PvE FLEET controller (rewritten at Story 5.6 from the weaponless target-drone controller it replaces). A fleet ship is an ordinary `role='fleet'` hull; the controller is its hands, submitting a sanitized `InputMsg` through the exact `World.submitInput` path a human uses.
- **game/ai/** — COMBAT BOTS (`role: 'bot'`): types.ts (the perception boundary), botDriver.ts (hands and eyes — observe every tick, deliberate on cadence), utility.ts (world model, target + posture), profiles.ts (two priority profiles per class; temperament, NOT a difficulty ladder), equipment.ts (`EquipmentTactic` — weapon knowledge travelling with the weapon), tactics.ts (helm, weapon choice, aim), spending.ts (boon policy). ESLint STRUCTURALLY forbids `ai/` from importing `world.js`; a bot's entire world is a bound per-bot observe thunk.
- **game/spawn.ts** — spawn-ring placement (max-min distance from existing ships, island-clear).
- **game/lead.ts** — THE intercept solver, shared by everything on the server that shoots at a moving hull (the fleet gun, the captive mine's fish).
- **game/bounty.ts** — the KILL LEADER held-throne rule over participant kills (strict overtake only; a tie never transfers). Pure, zero Colyseus imports.
- **game/regatta.ts** — Regatta Hoist personal-hue assignment: the ONLY source of a player's wheel index (first-come-first-served at join, nearest free on collision, never changes mid-match).
- **game/rtt.ts** — windowed-minimum RTT estimator per client, feeding the D1 fire-time back-date clamp.
- **game/combat.ts** — compatibility re-export of gun fire control (moved into equipment/guns.ts).
- **game/equipment/** — `Equipment` interface + registry (index.ts): guns.ts, torpedoes.ts, mines.ts, broadside.ts, starShells.ts, radarBuoy.ts, boost.ts (the one non-weapon, instant-activation ability), plus shared ballistics.ts and ammo.ts. The gun is the permanently-selected default weapon; the specials are prime-next-shot skillshots on Q/E/R. A click carries `input.slot` (the resolved prime; the server keeps no priming state), and every fitted slot's reload ticks every tick regardless of which is primed.

### Code Quality Conventions
- **Cyclomatic complexity ≤ 10** — Enforced by ESLint (`complexity: ["error", 10]`). All functions must stay under this limit.
- **~500 LOC per file** — Soft convention, not enforced. Files may exceed this when the content is cohesive.
- **One-way client data flow** — server mirror (net) → sim state (prediction) → render views. state.ts is a leaf (no heavy app imports); render modules never drive net/sim.
- **Sim purity** — `shared/` is pure functions over plain objects (zero I/O); `server/src/game/world.ts` and `game/match.ts` have zero Colyseus imports so they stay unit-testable.

### Key Decisions
- **CONFIG is the single source of truth** — every gameplay-authoritative tunable lives in `shared/src/constants.ts` (`CONFIG`). Client-only feel knobs live in `client/src/config.ts`; promote a value to shared CONFIG the moment it becomes gameplay-load-bearing.
- **Deterministic shared simulation** — the same pure functions (`stepShip`, `stepShell`, `generateMap`, zone math) run on server and client. This is what makes client-side prediction agree with the authoritative world. `PROTOCOL_VERSION` (shared/src/index.ts, currently 48) records wire-breaking changes and IS a runtime join gate: `server/src/rooms/roomOptions.ts` (`protocolVersionError`) rejects a mismatched-or-missing client `pv` at matchmake time, before any seat is reserved.
- **effectiveStats() is the boon desync firewall** — (ship class + fitted boons) → every derived stat, via one pure function both sides call. Server caches it on grant/spawn; client recomputes from `you.cls` + `you.boons`. Every DERIVED field is re-pinned POST-fold inside it (`sightRange = radarRange / 2`, the `rangeU` paths, `cooldownScale`, `mine.triggerRadius`) and removed from `BOON_STAT_PATHS`, so nothing can address it directly. Nothing may re-derive a boosted stat ad hoc.
- **Boon offers are pre-drawn at earn-time** — a banked LEVEL carries a fixed offer of `CONFIG.offer.size` (4) DIFFERENT card LINES drawn from that player's own deck (`sim/deck.ts` `drawOffer`, weighted by rarity), materialized once and held server-side as `BoonOffer`. Reopening the refit window can never reroll (FR19). The category-first roll and `rollOffer()` died wholesale at Story 2.8 (amendment 38). **The refit window is `Tab` to open, `1`–`4` to take a card, `5` for DAMAGE CONTROL (`HEAL_CHOICE`)** — verified in `client/src/input/keyboard.ts`; there is no `CTRL` binding of any kind, and UX-DR14's SPACE hold-not-toggle is RETIRED (cycle 126).
- **Authoritative 20Hz World, zero Colyseus imports** — `game/world.ts` owns the one server clock and runs a fixed 50ms step; `ArenaRoom` is a thin adapter. The room's only synced schema is the roster.
- **frames.ts is the single spatial chokepoint (anti-cheat)** — everything spatial leaving the server goes through per-client frame construction, and its contacts/events come EXCLUSIVELY from `perception.observe()`. Property-style invariant tests enforce that no contact/event references anything outside sight ∪ this-tick radar paints. Clients are never sent what their sight or sweep hasn't legitimately revealed.
- **Sensor tiers on ONE ruler, and TWO occlusion rules** — every sensor boundary is a named eighth of INTEL RANGE (the Eighths Ladder, below): 3/8 `detect` 247.5u, 4/8 `sight` 330u, 5/8 `muzzleFlash`/smoke 412.5u, 7/8 `farRadar` 577.5u, 8/8 `radar` 660u — all frozen at base for every observer since cycle 119. True-sight bubble (`dist ≤ sightRange`, LOS-clear → live contacts) and radar (sight < dist ≤ radar, beam crossed the bearing this tick → `blip` events). **LOS is BINARY for every sensor except radar**: `losClear` = the observer→point segment crosses no island circle, and its five non-radar callers are untouched. **The radar gate alone is height-aware** — `radarShadow.visibilityTo(...) > 0`, an accumulating march against the height raster, so a low island no longer hides a distant ship (Story 4.11). Ships, WAKES and radar buoys paint; a jamming buoy makes the server emit deliberate FAKE blips through the same gate and shaper. Phosphor decay is client render math (the server keeps no blip history).
- **Per-event visibility rules** — shells/torps materialize at the sight boundary with current pos/velocity only (no range-derivable fields, so the wire can't be solved back to the muzzle); a boom's victim id is stripped unless the victim's center is sighted; damage is victim-private; upgrade/point events are self-private (enemy builds and point banks never ride on contacts).
- **Client prediction + reconciliation** — own ship is stepped locally each 50ms tick with a ring of un-acked inputs; every server frame drops acked inputs and replays the rest. Contacts are snapshot-interpolated (~-100ms). `P` toggles prediction ⇄ raw interpolation for debugging.
- **Fog is a pre-baked texture composite** — dark overlay with a feathered sight hole, conic sweep wedge, timestamp-decayed blips. DOM is used only for chrome — home, settings, refit, results, kill feed, and the `/privacy` + `/how-to-play` pages; everything tactical is Pixi.
- **Match lifecycle is a pure state machine** — `game/match.ts` (waiting/gathering/countdown/live/results), zero Colyseus imports. Since Story 6.1 the WAIT lives in `StandardQueueRoom`, not the arena: `CONFIG.match.joinWindow` is 0 (the arena's own gathering window is RETIRED in production but kept reachable via `matchOverride`), the queue holds a pool for `queueTimerMs` (2:00) once it arms at `minHumans`, and the arena's countdown is the final 10s beat. A boarding grace backstops the wait for the last loader. The win check counts afloat CAPTAINS — participants, so bots contest it and a bot may legitimately win (`isParticipant` = `role !== 'fleet'`); only PvE fleet hulls are excluded. A sinking hull is not win-eligible, but the transition is HELD OPEN until no captain is still in its sinking window.
- **Three ship classes, three FITS** — Torpedo Boat (fast/light, hp 250), Battleship (slow/heavy, hp 350), Mine Layer (mid, hp 300); hull dims, hp and kinematics vary. The "universal weapon fit" of the prototype is GONE: since Stories 1.6–1.8 (and Story 7-5 wave 2) each hull carries its own loadout — TB `[gun, torpedo, speedBoost, —]`, BS `[gun, broadside, starShells, —]`, ML `[gun, mine, radarBuoy, —]` — with the 4th slot open for an ACQUISITION card. Only the PvE fleet keeps `[gun, torpedo, mine, —]`. The gun is universal and shared. (The retired destroyer/cruiser/battleship prototype kinematics now live on as the PvE fleet envelopes, byte-for-byte, pinned by a shipClasses identity test.)
- **The universal standard gun (Eric ruling 2026-07-21)** — the permanently-selected default weapon: 360° (no mounts/arc), a single shot on a 5s reload (a 1-round pool, presented as a pure cooldown; 2.5s at a max global-cooldown build — Eric ruling 2026-08-04, was 3s base), that flies to the CLICKED point and BURSTS there in `burstRadius` (every enemy hull in range takes full damage; an early interceptor takes the smaller `contactDamage` and stops the shell with no burst, unless inside the would-be blast). ### Custom deploy hooks
- Pre-merge: none
- Deploy trigger: automatic on push to the service's own branch (Render auto-deploy)
- Deploy status: poll the URL of whichever environment was deployed
- Health check: https://hullcracker.io/ for production; https://hullcracker-dev.onrender.com/ after a staging deploy — never health-check production after a staging deploy. **Once `HC_STAGING_KEY` is set, a healthy staging host answers `401`, not `200`** — that is the password page doing its job, not a failed deploy. `200` there means the gate is OFF.

### The two environments

Each service still serves the built client AND the Colyseus game process from one process; this is an ENVIRONMENT split, not a service split. Story 7-7 *would* split frontend from backend and is DEFERRED IN FULL (Eric ruling F2, 2026-08-21) — do not pre-empt it.

**`render.yaml` is live configuration, not documentation.** Render Blueprint `salvobp` has autoSync ON against it on `main`. Adding a service there creates and bills it; changing `plan` there changes the instance being paid for. Never reach for the Render API or dashboard to make a config change that belongs in the file — the file is the source of truth, and drift between the two is what cycle 127 existed to clean up.

| | production | staging |
|---|---|---|
| Service | `hullcracker` | `hullcracker-dev` |
| Branch | `main` | `development` |
| Plan | pro (2 CPU / 4 GB) | starter (0.5 CPU / 512 MB) |
| Analytics / ads | GA4 + AdSense live | **neither** — both absence-gated off |
| Indexable | yes | no (`HC_NOINDEX=1` → `X-Robots-Tag`) |
| Access | public | **shared password** (`HC_STAGING_KEY`) |

**The staging password.** Set `HC_STAGING_KEY` in the Render dashboard for `hullcracker-dev` (it is `sync: false` in `render.yaml`, so the value is never committed). Visiting the host shows a password page; entering it sets a cookie and you are in. Hand the same password to a playtester. **To rotate, change the env var** — every issued cookie is a digest of the old key, so all of them stop matching at once and everyone is re-prompted. Leave the var unset to run staging open.

It gates **two** doors with one secret, and both are required: an Express middleware in front of `express.static` for the page, and `stagingGateError()` in **both** rooms' `static onAuth` for matchmaking. An Express-only gate would be a facade — `/matchmake/*` and the socket never enter Express, so the game server would stay open. Gating only the queue would likewise leave SOLO VS AI open, since it reaches the game through `client.create('arena')`. `/liveness` and `/metrics` stay open, and a mid-match reconnect is not re-gated (the resume token is the auth) — the same posture the `PROTOCOL_VERSION` gate has always had.

### The development flow
1. Branch from `development` (**not** from `main`).
2. Build the feature; open the PR against `development`.
3. Merge to `development` → the dev service auto-deploys.
4. **Manual QA on the dev host.** This is the gate.
5. Only once QA passes, merge `development` → `main` → production auto-deploys.

**If anything ever lands on `main` directly** — an emergency hotfix, or the bootstrap PR that created this setup — merge `main` back into `development` immediately. Otherwise `development` is behind, the next feature branches from stale code, and the fix is silently re-reverted the next time `development` merges up.

**What the staging gate cannot catch.** Two known blind spots, both structural — do not read "QA passed on staging" as "safe":
1. **Performance.** Staging is `starter` (0.5 CPU / 512 MB) against production's `pro`. Functional QA is trustworthy; frame timings are not. A 20-hull SOLO VS AI match is where the gap shows. Raise the dev plan in `render.yaml` for a cycle that needs to trust its own numbers.
2. **Analytics and ads.** Because staging deliberately omits `VITE_GA_MEASUREMENT_ID` and `VITE_ADSENSE_CLIENT`, the code behind them never runs there — `analytics/consent.ts`, `consentMarker.ts`, `ga.ts`, `ads/adsAdapter.ts`, `adsense.ts`, `resultsAd.ts`, and the interstitial call site in `app/returnToPort.ts`, which takes a *different branch* on staging than in production. Those are the most third-party-fragile modules in the repo and they reach production unexercised. A change touching any of them needs a production smoke immediately after merge.
